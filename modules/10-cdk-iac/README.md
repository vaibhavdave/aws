# Module 10 — Infrastructure as Code (CDK)

## Theory

**Infrastructure as Code** means your infrastructure's definition lives in a
file, in version control, reviewed like any other change — instead of living
in whatever state someone last left the console in. **CloudFormation** is
AWS's native IaC engine: you give it a template (JSON/YAML describing
resources), it diffs that against what's actually deployed (a **change set**)
and applies the difference. Every module before this one used the AWS SDK
directly to *imperatively* call `CreateTable`, `CreateFunction`, etc. one at
a time, in your own code, with your own idempotency handling
(`try { create } catch (AlreadyExists) { get }` — a pattern you've now
written by hand in Modules 01, 03, 05, 06, 07, 08, and 09). CloudFormation
(and CDK on top of it) does that diffing/idempotency for you.

**CDK generates CloudFormation, it doesn't replace it.** `cdk synth` turns
your Java (or TypeScript/Python/Go) code into a plain CloudFormation
template; `cdk deploy` submits that template to CloudFormation, same as if
you'd hand-written the YAML. This module's `TaskTrackerStackIT` proves this
directly: it synthesizes the stack and asserts on the *resulting
CloudFormation JSON*, never touching CDK's deploy machinery at all.

**L1 vs. L2 constructs:** an L1 construct (`CfnTable`, `CfnFunction`, ...) is
a 1:1 mapping to a CloudFormation resource — same fields, same verbosity. An
L2 construct (`Table`, `Function`, `LambdaRestApi`, all used here) adds
sensible defaults and convenience methods on top. `taskTable.grantReadWriteData(apiFunction)`
is the clearest example: it inspects what the function actually needs and
generates a scoped IAM policy — compare that one line to Module 01's
hand-written `task-tracker-app-policy.json`, or `LambdaRestApi.Builder.create(...).proxy(true)`
to Module 06's `ApiGatewayAdmin` building `/tasks` and `/tasks/{id}` one
`putMethod`/`putIntegration` call at a time.

## What you'll build

`TaskTrackerStack` recreates Module 06's infrastructure declaratively:

- A `task-tracker` DynamoDB table with the same `owner-index` GSI and stream
  configuration Module 03 built by hand via `TaskTableAdmin`.
- A Java 21 Lambda function running Module 06's own `TaskApiHandler`
  (this module builds its own copy of that jar via its own shade-plugin
  execution, so it's self-contained rather than reaching into another
  module's `target/`).
- An IAM policy generated by `grantReadWriteData`, not typed by hand.
- A REST API via `LambdaRestApi` with `proxy(true)` — a single greedy
  `{proxy+}` resource forwarding everything to the function.

## Running it

Synthesizing and testing the stack needs nothing but Java/Maven:

```bash
mvn -pl modules/10-cdk-iac -am verify
```

Actually deploying it needs the `cdk` CLI (Node.js) and a running Floci:

```bash
npm install -g aws-cdk
docker compose up -d
mvn -pl modules/10-cdk-iac -am package    # builds target/task-tracker-lambda.jar

cd modules/10-cdk-iac
export AWS_ENDPOINT_URL=http://localhost:4566
export AWS_ACCESS_KEY_ID=test
export AWS_SECRET_ACCESS_KEY=test
export AWS_DEFAULT_REGION=us-east-1

cdk bootstrap aws://000000000000/us-east-1 --toolkit-stack-name CDKToolkit
cdk deploy
# ... use the stack ...
cdk destroy
```

`cdk bootstrap` provisions CDK's own staging resources (an S3 bucket, IAM
roles) via CloudFormation - Floci's in-process CloudFormation emulation is
what makes this work locally at all, the same as it would against real AWS.

## Tests

```bash
mvn -pl modules/10-cdk-iac -am verify
```

`TaskTrackerStackIT` is a failsafe IT (needs `target/task-tracker-lambda.jar`
to exist first, same reasoning as Modules 05/06) that synthesizes the stack
and asserts on the resulting template: the table's billing mode, stream
config, and GSI; the function's handler and runtime; the API's proxy
resource; and that the generated IAM policy is scoped to specific DynamoDB
actions rather than `"Action": "*"`. Unlike every other module's
Floci-tagged integration test, this one needs no Docker and no `-Pfloci` -
CDK's `Template` assertions are pure in-process synthesis.

## Checkpoint

- What does `cdk synth` actually produce, and what turns that into running
  infrastructure?
- Why can `TaskTrackerStackIT` verify real behavior without Docker, when
  every other module's deployment test couldn't?
- If you added a second Lambda function to this stack, what would you
  need to change in `TaskTrackerStackIT` to keep verifying least-privilege
  IAM, and why?
